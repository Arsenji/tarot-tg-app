# 📋 Полный список проблем продукта Tarot Telegram App

## 🔴 КРИТИЧЕСКИЕ ПРОБЛЕМЫ

### 1. Архитектурные проблемы

#### 1.1. Дублирование структуры проекта
- **Проблема**: Скомпилированные файлы присутствуют в корне проекта
- **Файлы**: `dist/`, `bot/`, `config/`, `models/`, `routes/`, `services/`, `types/`, `utils/`, `middleware/` в корне
- **Риск**: Запутывание структуры, непредсказуемое поведение при развертывании
- **Решение**: Удалить все скомпилированные файлы из корня, оставить только исходники в `backend/src/`, `frontend/src/`

#### 1.2. Несоответствие в структуре backend
- **Проблема**: Backend скомпилирован в `backend/dist/`, но также присутствует в корне
- **Риск**: Дублирование кода, непонятная структура деплоя
- **Решение**: Удалить скомпилированные файлы из корня, использовать только `backend/dist/`

#### 1.3. Отсутствие централизованного Dockerfile
- **Проблема**: В корне есть Dockerfile, который не соответствует текущей структуре
- **Риск**: Невозможность корректного деплоя через Docker
- **Решение**: Обновить корневой Dockerfile или удалить его

### 2. Проблемы с зависимостями

#### 2.1. Дублирование зависимостей
- **Проблема**: Зависимости определены и в корневом `package.json`, и в `backend/package.json`
- **Риск**: Конфликты версий, проблемы при установке
- **Решение**: Переместить все общие зависимости в корневой `package.json`, использовать workspaces

#### 2.2. PostgreSQL в корневых зависимостях
- **Проблема**: В корневом `package.json` есть `pg` (PostgreSQL), но проект использует MongoDB
- **Риск**: Лишние зависимости, путаница
- **Решение**: Удалить `pg` из корневого `package.json`

#### 2.3. Несогласованность версий
- **Проблема**: Разные версии одних и тех же пакетов в разных workspace
- **Риск**: Непредсказуемое поведение, сложность отладки
- **Решение**: Унифицировать версии через корневой `package.json`

### 3. Проблемы с конфигурацией

#### 3.1. Множество .env файлов
- **Проблема**: `env.example`, `docker.env.example`, `docker.env.secure`, `backend/.env`, `admin-backend/env.example`
- **Риск**: Запутывание в настройке окружения
- **Решение**: Создать единый `.env.example` для всех сервисов

#### 3.2. Отсутствие валидации переменных окружения
- **Проблема**: Нет централизованной проверки обязательных переменных
- **Риск**: Приложение может запуститься без критических переменных
- **Решение**: Добавить валидацию при старте всех сервисов

#### 3.3. Несоответствие портов
- **Проблема**: Разные порты указаны в разных местах (3001, 3002, 3003)
- **Риск**: Конфликты портов, неправильное подключение сервисов
- **Решение**: Установить четкую схему портов в документации

### 4. Проблемы безопасности

#### 4.1. Возможное хранение секретов в коде
- **Проблема**: В `YOOKASSA_DEBUG_REPORT.md` были реальные ключи (уже заменены на placeholders)
- **Риск**: Утечка секретных данных
- **Решение**: Аудит всех MD файлов на наличие реальных ключей

#### 4.2. Слабая защита от brute-force
- **Проблема**: Нет rate limiting на критических endpoints (логин, создание платежей)
- **Риск**: Атаки на аутентификацию и платежи
- **Решение**: Добавить строгий rate limiting

#### 4.3. Отсутствие валидации входных данных
- **Проблема**: Не все endpoints проверяют входные данные
- **Риск**: SQL/NoSQL injection, XSS
- **Решение**: Добавить middleware валидации на все endpoints

### 5. Проблемы с базой данных

#### 5.1. PostgreSQL в зависимостях
- **Проблема**: В корневом `package.json` есть `pg`, но проект использует MongoDB
- **Риск**: Лишние зависимости
- **Решение**: Удалить `pg` и связанные зависимости

#### 5.2. Отсутствие миграций
- **Проблема**: Нет системы миграций для MongoDB
- **Риск**: Сложность обновления схемы БД
- **Решение**: Добавить mongoose-migrate или аналог

#### 5.3. Нет подключения к Redis
- **Проблема**: Redis настроен в docker-compose, но не используется в коде
- **Риск**: Неэффективная работа с кэшем
- **Решение**: Подключить Redis для кэширования

## 🟡 СРЕДНИЕ ПРОБЛЕМЫ

### 6. Проблемы с кодом

#### 6.1. Отсутствие обработки ошибок
- **Проблема**: Не все async функции имеют try-catch
- **Риск**: Непредсказуемые падения приложения
- **Решение**: Добавить централизованную обработку ошибок

#### 6.2. Дублирование кода
- **Проблема**: Похожий код в разных местах (например, валидация токенов)
- **Риск**: Сложность поддержки
- **Решение**: Вынести общую логику в utils

#### 6.3. Отсутствие логирования
- **Проблема**: Многие операции не логируются
- **Риск**: Сложность отладки в production
- **Решение**: Добавить структурированное логирование

### 7. Проблемы с API

#### 7.1. Отсутствие версионирования API
- **Проблема**: Нет версии в URL (`/api/v1/...`)
- **Риск**: Сложность обновления без breaking changes
- **Решение**: Добавить версионирование API

#### 7.2. Нет документации API
- **Проблема**: Отсутствует OpenAPI/Swagger документация
- **Риск**: Сложность разработки frontend/интеграций
- **Решение**: Добавить Swagger документацию

#### 7.3. Отсутствие CORS настройки
- **Проблема**: CORS настроен слишком открыто (`cors()` без параметров)
- **Риск**: Небезопасные запросы
- **Решение**: Настроить CORS для конкретных доменов

### 8. Проблемы с frontend

#### 8.1. Множество useEffect без cleanup
- **Проблема**: Отсутствует cleanup в некоторых useEffect
- **Риск**: Memory leaks
- **Решение**: Добавить cleanup функции

#### 8.2. Хардкод URL
- **Проблема**: URL API хардкодятся в коде
- **Риск**: Сложность переключения между dev/prod
- **Решение**: Использовать переменные окружения

#### 8.3. Отсутствие error boundaries
- **Проблема**: Нет error boundaries в React
- **Риск**: Весь app падает при ошибке
- **Решение**: Добавить Error Boundaries

### 9. Проблемы с Telegram Bot

#### 9.1. Отсутствие обработки webhook
- **Проблема**: Бот запускается через polling, нет webhook
- **Риск**: Неэффективное использование ресурсов
- **Решение**: Перейти на webhook

#### 9.2. Нет обработки ошибок Telegram API
- **Проблема**: Не обрабатываются ошибки от Telegram API
- **Риск**: Падения при недоступности API
- **Решение**: Добавить retry логику и graceful degradation

#### 9.3. Отсутствие очереди для сообщений
- **Проблема**: Сообщения отправляются сразу, без очереди
- **Риск**: Превышение rate limits Telegram
- **Решение**: Добавить очередь для отправки сообщений

## 🟢 НИЗКИЕ ПРОБЛЕМЫ

### 10. Проблемы с производительностью

#### 10.1. Отсутствие индексов в MongoDB
- **Проблема**: Не все часто запрашиваемые поля проиндексированы
- **Риск**: Медленные запросы
- **Решение**: Добавить индексы на `telegramId`, `userId`, `createdAt`

#### 10.2. Нет кэширования запросов
- **Проблема**: Повторные запросы идут в БД без кэша
- **Риск**: Лишняя нагрузка на БД
- **Решение**: Использовать Redis для кэширования

#### 10.3. Большой размер bundle
- **Проблема**: Frontend bundle может быть излишне большим
- **Риск**: Медленная загрузка
- **Решение**: Настроить code splitting

### 11. Проблемы с тестированием

#### 11.1. Отсутствие тестов
- **Проблема**: Нет unit/ integration/ e2e тестов
- **Риск**: Высокая вероятность регрессий
- **Решение**: Добавить тесты для критических частей

#### 11.2. Нет CI/CD
- **Проблема**: Отсутствует автоматизированный деплой
- **Риск**: Ручной деплой, возможные ошибки
- **Решение**: Настроить GitHub Actions/GitLab CI

### 12. Проблемы с документацией

#### 12.1. Устаревшая документация
- **Проблема**: README не соответствует текущей структуре
- **Риск**: Сложность для новых разработчиков
- **Решение**: Обновить всю документацию

#### 12.2. Отсутствие архитектурной документации
- **Проблема**: Нет описания архитектуры системы
- **Риск**: Сложность понимания системы
- **Решение**: Создать диаграммы архитектуры

### 13. Проблемы с Docker

#### 13.1. Большой размер Docker images
- **Проблема**: Images содержат dev зависимости
- **Риск**: Большой размер, медленный деплой
- **Решение**: Использовать multi-stage builds

#### 13.2. Отсутствие health checks
- **Проблема**: Нет health checks в Docker
- **Риск**: Некорректное определение работоспособности
- **Решение**: Добавить health checks в docker-compose
